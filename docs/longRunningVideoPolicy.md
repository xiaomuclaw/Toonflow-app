# 视频跨小时、跨天等待与恢复方案

日期：2026-10-08。状态：设计稿，尚未实施。针对用户追加的“上游可能生成几十分钟、几小时或几天，本地不要因超时误判失败”。与原执行任务书合用；本文件细化长期等待语义，不要求重写架构。

## 1. 交付行为

提交后先可靠保存任务编号并返回。上游还在排队或生成，无论等待多久，本地继续跟进；一次查询超时只代表这次没有查到进度。上游已经生成成功但文件没下载完，继续下载原结果。

默认不按总时长自动判失败。等待超过 24 小时仅在现有节点和任务查询结果中提醒，提醒小时数可修改，0 表示不提醒。没有“到时自动重新生成”，也不默认发送邮件或其他外部通知。

保留单账号、单进程、Bun / TypeScript / Express、现有文件持久化和现有任务接口；不新增 Redis、消息服务或复杂任务中心。已有任务接口、设置面板、节点状态条足以承载。

## 2. 当前实现的准确边界

| 路径 | 当前行为 | 本次需要解决的事 |
| --- | --- | --- |
| Dola 的持久任务 submitMedia / queryMedia | 不继承旧同步函数的 12 小时总超时 | 查询错误分类、下载分离、长期调度和恢复还不完整 |
| Dola 的旧 generateVideo | 有 12 小时总超时 | 不作为跨天生成入口 |

| Metaso 的同步视频 | 约 10 分钟总超时 | 同上；本轮按原范围保留条件项，界面说明能力差异 |

## 3. 四种时间分别管理

以下数值是首版建议值，不是当前已实现配置。网络超时使用每次请求自己的 AbortController，与服务停机信号合并；一次尝试被中断后，不沿用已经 aborted 的 controller。

| 时间 | 建议默认值 | 到时如何处理 |
| --- | --- | --- |
| 提交上游的一次网络尝试 | 90 秒 | 无上游 ID 且无法确定受理情况时，保留提交键，进入待核对；不再次创建 |
| 查询上游的一次网络尝试 | 30 秒 | 有上游 ID 就保留原任务，安排下一次查询 |
| 下载的一次尝试 | 连续无数据 60 秒；单次总尝试 15 分钟 | 保留已成功输出，继续补下载；仍执行现有媒体大小限制 |
| 整个视频的生成等待 | 不限时 | 24 小时起提醒，可调；不因本地时长转 failed |

下载尝试上限不是下载任务总寿命。网络过慢时可在高级配置调整单次值；断点续传只在上游明确支持 Range 且结果身份一致时使用，不为首版强加新的下载系统。

MCP / HTTP 客户端本身的通信时限仍然保留。客户端断开只结束观察；已经受理的服务器任务拥有独立生命周期。未受理的请求不能虚报 accepted。

## 4. 最小状态契约

沿用 preparing / queued / submitting / running / downloading / succeeded / failed / cancelled / unknown。不要为每种网络异常增加一种主状态；在任务记录中补充少量跟进信息。

| 事实 | 主状态与跟进方式 | 用户看到的含义 |
| --- | --- | --- |
| 输入准备中 / 等执行额度 | preparing / queued | 等待提交，尚未声称上游开始生成 |
| 已取得上游 ID，上游未终结 | running | 上游排队或生成中；展示已等待时间 |
| 查询断网、超时、临时 5xx、429 | 保持 running，记录重试时间和原因 | 暂时无法查询，稍后继续 |
| 查询凭据失效、账户不匹配、适配器不兼容 | 保持已有业务事实，跟进暂停为 blocked | 查询受阻，需要处理；并不代表上游失败 |
| 提交响应丢失、尚无可确认的上游 ID | unknown，作为待核对状态保留 | 提交结果待确认；不能自动再生成 |
| 上游成功、下载或保存尚未完成 | downloading | 上游已完成，正在取回结果 |
| 有效成片可靠落盘并登记输出 | succeeded | 可下载；画布保存是否成功另行显示 |
| 上游明确报告生成失败 | failed | 生成失败，保留上游状态及去敏原因 |
| 确认未发往上游就取消，或上游明确确认取消 | cancelled | 已取消；区分取消发生在哪一侧 |
| 用户停止浏览器观察 / 关闭网页 | 服务器状态与跟进方式均不变 | 网页不查进度，服务器仍查询、下载和保存 |
| 用户明确选择暂停服务器跟进 | 保留主状态，服务端跟进标记 paused | 服务器停止查询，上游可能仍继续生成 |

建议复用 retryAt / retryCount，新增或明确 lastQueryAt、lastQuerySucceededAt、lastUpstreamState、trackingStatus、waitingReason、resultReadyAt 等字段。trackingStatus 只需 active / blocked / paused。现有 taskId、batchKey、itemKey、upstreamId、输入快照和 providerRevision 继续使用。

unknown 不再等同于“可以忘记的终态”。没有 ID 的 unknown 不自动运行提交动作；保留输入、幂等键、关联和人工核对入口。已有 ID 的任务禁止因为一次查询失败滑入不可恢复终态。

网关返回 502 不能证明提交未受理。只有提交前校验失败，或供应商契约明确证明未受理，才可以记录确定失败。失败、重试与取消分类不能仅依赖 HTTP 状态码或 error instanceof Error；跨 VM 读取可验证的结构化字段。

## 5. 查询、重启与容量

### 5.1 分开本地执行槽和上游在途额度

- 现有 generationConcurrency 的语义固定为上游尚未终结的生成额度，默认继续使用 2；不是一批只能有 2 项，更不是总共只能提交 100 项。
- 单次提交、查询使用短时执行槽；查询间隔不占用 HTTP 执行槽。已有上游任务仍占在途额度，不能因此无限放行新生成。
- 下载继续用独立 downloadConcurrency。Dola queryMedia 只返回状态和结果定位信息，不在查询函数里完整下载成片。
- 重启先恢复已知上游 ID 和下载中的任务，统计在途数量，再放新 queued。恢复时已有数量超过配置，就先禁止新增上游任务，继续查已有任务。
- 无 ID 的提交待核对任务、尚未确认上游终结的暂停跟进任务，保守占用可能存在的在途额度。解除额度需确认结果，或由用户明确知情处理，不能自动释放后重复收费。

### 5.2 查询退避

服务器查上游可先采用：前 5 分钟约每 10 秒，5～30 分钟每 30 秒，30 分钟～2 小时每 60 秒，2 小时后每 5 分钟；增加约 20% 抖动。5 分钟只是首版默认上限；须结合已确认的上游结果/链接保留期调整，不能保证赶上尚未核实的短有效期链接。

临时网络错误使用 10 秒起的指数退避，通常封顶 5 分钟；成功查询后恢复所属等待阶段的频率。有效 Retry-After 是最早重试时间，不得因为本地 5 分钟封顶反而提前请求。401 / 403 等查询受阻应停止密集重试，等待配置修复或手动继续。

本地网页查服务器只读任务快照，不让每次 getVideoTasks 再去等上游。复用一次最多 200 个 taskId 的查询能力，合并同工作区的节点查询；后台标签可以减少状态轮询，但必须保持 MCP 控制连接可用。回前台、网络恢复、重新登录后立即补查。

### 5.3 重启恢复

关键状态、上游 ID、next retry 时间和成功输出逐步 durable 保存。启动先加载恢复记录，再标记调度就绪；不要让健康接口只因目录可写就声称恢复完成。

服务退出先停止新受理/提交并清理启动定时器，让在途作业安全中止或收敛；已收到上游 ID 的持久化临界段必须先完成。等待在途作业结束后，再最终排空写队列，避免第一次排空之后又出现迟到写入。宽限结束仍未收敛的任务保留最后可靠状态，不写成生成失败；下次按原 ID 继续。

## 6. 输入、结果和网页关联

1. 任务关联至少包含 directory + canvasId + nodeId + batchKey + itemKey + taskId。提交前把稳定键写入可恢复位置；不能只靠当前组件内存。
2. 网页没收到 taskId 时，只按原 batchKey 发 GET 查询并按 itemKey 找回，不从恢复入口触发 submit。短暂查不到记录不是未受理的证明；不得三次空查询后删除关联并提示重新生成。
3. 收到 taskId 就结束受理动作，首次进度查询异步执行。网页节点不能返回没有 taskId 的 accepted。
4. 任务输出写到节点内存后，关联保持“已完成、待保存”。画布成功以正确 revision 落盘，才能清理临时恢复关联；409、断网、退出都保留恢复依据。
5. 重新登录只恢复查询和待保存内容，不重放生成。统一处理 Axios、工作区客户端和任务 fetch 的 401；禁止强制 reload 丢草稿。
6. 同一画布多个窗口使用打开时的 revision；首次保存不能临时读取最新 revision 为旧内容背书。冲突允许保留草稿、重新读取和人工合并。
7. 首次 attach 失败后允许再次恢复，不永久缓存失败 Promise。停止网页观察后可明确继续查询，恢复不要求重新填写模型或提示词；浏览器停止观察不能更改服务器 trackingStatus 或在途额度。

## 7. 下载、自动清理与供应商变更

- 查询到上游成功后进入 downloading；下载 403 / 链接过期时用原 upstreamId 重新查询。上游支持刷新时取得新定位；不支持或已删除结果则显示待核对/无法补取，不能假定重新查询总能刷新链接。网络暂时失败仍保持 downloading，绝不回到提交生成。
- 输出用稳定任务/资产身份登记，已经保存的逐项保留。落盘和登记之间重启后应能认回原文件，不能只靠“内存里已有 outputs”去重。
- 自动清理保护所有在途、待核对、待下载、暂停跟进但尚未解决的任务所需数据。不要把这些状态当普通两天缓存。
- 每个生成结果的清理计时起点取“实际可靠落盘时间”与“最后一次实际占用保护解除时间”的较晚者，不从几天前提交时起算。部分结果先完成、整个任务几天后才结束时，解除保护后仍获得完整保留期；普通预览不延长计时。
- 原始资料默认 30 天、五类默认关闭的既有要求不变。启用清理后，任务引用、编辑占用、多个归属和持久清理标记必须一致，删除前重查。
- 当前 providerRevision 是整个供应商源码的 SHA-256。不要直接去掉校验，也不要在任何升级后把旧任务不可逆转为 unknown。首版由受控兼容规则允许继续查询已知兼容版本；其余保持 blocked，提供恢复原任务查询入口。
- Key 轮换后重新加载同一账户的查询凭据。切换账户、供应商地址或不兼容协议须先核对任务归属；记录凭据引用，不把 Key 写入任务。

建议新增受保护的 POST /api/ai/media/tasks/resume，并由同一业务函数提供 MCP resumeVideoTasks。只恢复已有任务的查询或下载；不创建生成任务。无 ID 的任务需要绑定原上游 ID 时，校验工作区、供应商、账户和任务信息，核对失败保持原状态。接口、返回字段和旧取消记录的迁移规则由主控在开工门统一冻结。

旧 MCP generateVideo 保留返回结构兼容；明确描述同步等待和不适合长任务。服务器批量及跨天视频统一使用 submitVideoTasks / getVideoTasks；对不具备持久恢复能力的供应商显示明确能力说明，不暗示都能无限等待。

## 8. 必须说明的上游边界

本地能保证“不会仅因等待时长或查询超时而误判生成失败”，不能保证上游永远保留结果。上线说明要核对 Dola 的任务 ID 查询保留期、成片保留期、下载链接有效期以及能否刷新链接。

上游长期查不到记录、文件已删除或结果无法再次获取时，显示“待核对 / 结果无法取回”。保留原 ID 和历史，不伪装成生成失败，不自动重新付费提交。没有可验证的上游保留期资料时，明确标记未知，不编造天数。

## 9. 非付费验收与完成条件

禁止新增任何测试文件、临时测试程序、mock 服务或测试专用入口。按仓库规则执行类型检查、构建、手动产品 HTTP / MCP / 浏览器验证，保留原始证据。真实生产配置不得用改系统时间、改 DNS 或故障注入破坏；需要演练时使用隔离数据与已授权环境，不重复提交上游。

| 场景 | 必须核对的结果 |
| --- | --- |
| 已有上游 ID，长时间 running | 超过提醒阈值只提醒，原 ID / 主状态不因时长失效 |
| 多次查询断网、超时、5xx、429 | 继续保留任务，退避符合 Retry-After；不增加上游创建次数 |
| 提交首包丢失 | 用同一 batchKey / itemKey 找回任务；unknown 不导致自动重发 |
| 上游成功、下载中断 / 链接过期 | 保留 downloading，补取原结果，已有文件不丢失、不重复生成 |
| 401 与重新登录 | 草稿和关联保留；恢复查询，不重放生成 |
| queued 积压时服务恢复 | 先恢复旧在途任务，再按实际余量放新任务 |
| 供应商或 Key 更新 | 兼容更新继续查；不兼容明确受阻，并能按原 ID 恢复 |
| 清理与跨天等待相遇 | 活跃、待核对、待下载数据保留；成片保留期从落盘起算 |
| 停止观察、暂停服务器跟进再继续 | 网页停止观察不影响服务器；服务器暂停是独立明确操作，恢复仍使用原 ID，不要求重新填写生成参数 |
| 完成时画布保存失败 | 文件仍可找回，任务关联保留，409 不静默覆盖其他窗口 |

本轮已有 2 条真实成功视频和 2 次图生图，后续不得把它们误算为“还剩一条视频额度”。长时间自然运行证据、隔离恢复演练和源码推导分栏记录；几分钟的演练不能写成“已连续运行几天”。若某场景无法在现有限制内验证，列为未验证，不以扩大收费或新建测试程序补齐。

实施顺序：先冻结状态与恢复契约；任务后端、网页/MCP、文件归属与清理三路并行；共享类型和设置由主控集成；再统一构建、核对安装产物和验收。具体文件所有权与返工门槛见 deepseekRepairPrompt.md。
